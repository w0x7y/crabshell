how it fits together

two processes. your config compiles into the shell, and crabshell run rebuilds and restarts it. inside the shell, everything runs on one thread, around one event loop. select a part to see what it owns and what it talks to.

the crates

crate owns uses
crabshell-reactive signals, memos, effects, owners, flush none
crabshell-ui Cx, widgets, styles, layout, text, hit testing, what needs repainting reactive
crabshell-render drawing, damage, glyphs, icons and the icon theme lookup ui
crabshell-wayland the event loop, windows, popups, buffers, scale, pointer, monitors reactive, ui, render
crabshell-services sway workspaces, the tray, audio, the clock reactive, ui
crabshell run, per_output, cx.persist, the prelude, the control socket all of the above
crabshell-cli the crabshell command: init, check, run and the supervisor none of them

one turn of the loop

  1. the loop wakes when a source is ready: wayland, a d-bus reply, sway's socket, the audio thread or a timer.
  2. it runs that source's callback, which sets signals.
  3. flush re-runs the effects and bindings that read them, once each.
  4. windows whose layout changed are laid out again.
  5. each window with damage and a frame callback draws the damaged area into a shared-memory buffer.
  6. the wayland connection is flushed, and the loop sleeps until something else is ready.

nothing dirty means nothing drawn and nothing sent, so a bar whose only change is a minute clock wakes once a minute.

two processes

crabshell run is the supervisor. it builds the config with cargo, starts the shell, and listens on a socket whose path it passes in CRABSHELL_CONTROL. the shell says ready once every panel has drawn a frame. on a reload the supervisor sends save: the shell writes its cx.persist values and exits, and the new build starts from them.
