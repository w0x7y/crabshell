getting started

from nothing to a running bar, and what happens when you edit it.

what you need

  • rust 1.99 or newer
  • sway, or another wlroots compositor with layer-shell. labwc works too, though only sway shows workspaces for now
  • linux 5.3 or newer, for the supervisor's process handles
  • pkg-config, fontconfig and libpulse with their development files, like pkg-config libfontconfig1-dev libpulse-dev on debian or ubuntu
  • pulseaudio or pipewire-pulse running, for the volume widget
  • a d-bus session bus for the tray, and a notification daemon like mako or dunst for build errors

install the command

$ cargo install --locked crabshell-cli

that puts crabshell in ~/.cargo/bin. crabshell help lists its commands.

make a config

$ crabshell init

this writes ~/.config/crabshell from the template, a cargo project that depends on the crabshell crate. init never overwrites anything: it refuses if the directory is already there. to build against a clone of the repository instead, run crabshell init --path <clone>. 

~/.config/crabshell/
├── Cargo.toml
└── src/
    └── main.rs

the template is the v0.1 bar: sway's workspaces on the left, the tray, the volume and a clock on the right. writing a config walks through it line by line.

run it

$ crabshell run

the first build compiles the whole toolkit and takes a few minutes. later builds take about a second. builds go to ~/.cache/crabshell/target, so the config directory stays small.

to start it with sway, add this to your sway config. sway's exec may not see ~/.cargo/bin, so give the full path, and make sure cargo is on the PATH your session starts with: 

exec ~/.cargo/bin/crabshell run

run only one crabshell run at a time, or you get two bars.

edit and reload

leave crabshell run running and save src/main.rs or Cargo.toml. it rebuilds 300 ms after the last save.

  • when the build works, the old shell saves its cx.persist values and exits, and the new one starts from them. the bar is gone for about 20 ms.
  • when it doesn't, the old shell keeps running. the full error prints in the terminal, and a desktop notification shows its first line.
  • a save that changes nothing in the build doesn't restart anything.

when it crashes

  • a panic in one binding doesn't crash anything. that binding turns off, and the log names it, like PanelWindow[DP-1]/Row/Button[2]/Text.text.
  • a shell that dies starts again after 1 s, then 2, 4 and so on, up to 30 s.
  • a build that runs for a minute is copied to ~/.cache/crabshell/last-good.
  • when a new build crashes three times in its first minute, crabshell runs last-good instead, if there is one, and says so in a notification.

check without running

$ crabshell check

runs cargo check on the config and prints its errors, for editors and scripts. it exits with cargo's status.

logs

everything goes to stderr. the supervisor's lines start with crabshell:, and the shell's come from its log. set CRABSHELL_LOG=debug for more. to watch them, run crabshell run in a terminal instead of from sway.

where things live

path what
~/.config/crabshell your config: Cargo.toml and src/
~/.cache/crabshell/target its builds
~/.cache/crabshell/last-good the last build that ran for a minute
$XDG_RUNTIME_DIR/crabshell/state.json cx.persist values between two shells. written on reload, read once, then removed
$XDG_RUNTIME_DIR/crabshell/control-<pid>.sock the socket the supervisor and the shell talk over

XDG_CONFIG_HOME and XDG_CACHE_HOME move the first three.

exit codes

program code meaning
crabshell 0 stopped: the shell exited on purpose, the session ended, or it got ctrl-c or sigterm
crabshell 1 a command failed, and it says why
crabshell 2 the command line didn't parse, so it prints the usage
your shell 0 it saved its state for a reload
your shell 1 the closure passed to crabshell::run panicked
your shell 2 no compositor, a missing protocol, or the connection was lost
